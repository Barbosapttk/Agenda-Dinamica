Sumário executivo A ferramenta é uma aplicação web de arquivo único, baseada em HTML, CSS e JavaScript puro, com Supabase como backend de autenticação, persistência e Storage. O fluxo principal é: Nova Solicitação -&gt; Cliente vinculado -&gt; Fila de Orçamentos -&gt; Proposta enviada -&gt; Propostas em Acompanhamento -&gt; Controle de Vendas -&gt; Histórico / Relatório. O sistema utiliza uma estratégia de persistência por chaves JSON em uma tabela Supabase, além de um bucket de Storage para anexos de solicitações e clientes. A UI é uma SPA: as abas são views internas no mesmo HTML, exibidas/ocultadas por JavaScript, sem framework React/Next. O Controle de Vendas substitui a planilha mensal, alimentado automaticamente conforme propostas são registradas. 1. Persistência, Supabase e Storage A persistência principal usa uma tabela Supabase em modelo chave/valor, onde cada chave armazena um conjunto JSON da ferramenta. Isso evita criar muitas tabelas no banco durante a fase atual, mas exige cuidado na função de salvamento para manter os arrays consistentes. Chave lógica Nome salvo Conteúdo clientes secta_clientes Clientes cadastrados. contatos secta_contatos Contatos registrados, propostas enviadas por contato e logs comerciais. agendamentos secta_agendamentos Retornos, alarmes e compromissos comerciais. solicitacoesOrcamento secta_solicitacoes_orcamento Solicitações ainda em fila de orçamento. orcamentos secta_orcamentos Orçamentos recorrentes. concluidos secta_concluidos Retornos, solicitações e recorrentes concluídos / propostas registradas. historicoClientes secta_hist_clientes Histórico adicional de alterações em clientes. controleVendas secta_controle_vendas Linhas da planilha interna mensal de propostas/pedidos. alarmedIds secta_alarmed Controle de alarmes já tratados/soneca. theme secta_theme Preferência de tema claro/escuro. Storage de anexos: O bucket utilizado é agenda-dinamica-anexos. Solicitações e clientes salvam metadados do arquivo, caminho no Storage e URL/assinatura para visualização. Fluxos de negócio 5.1 Nova solicitação até proposta enviada Usuário clica em Nova Solicitação. Preenche cliente/contato, produto/serviço, tipo de orçamento, prazo, descrição e anexos. Se o cliente já existir, o sistema deve vincular a solicitação ao cliente existente, evitando duplicidade. A solicitação entra no Kanban da Fila de Orçamentos. Ao registrar proposta enviada, o cliente vinculado é obrigatório. O sistema cria registro em concluídos, alimenta o Controle de Vendas e exibe a proposta no Kanban de Propostas em Acompanhamento. 5.2 Status comercial x status do pedido Status comercial representa a negociação com o cliente e move o Kanban de Propostas. Status do pedido representa a etapa administrativa/financeira no Controle de Vendas. Os dois campos são independentes para evitar automações erradas. 5.3 Anexos Na Nova Solicitação, imagens e PDFs são enviados ao Supabase Storage. O registro salva metadados do arquivo, bucket, path, URL e informações de visualização. Ao reabrir a solicitação, a prévia usa Storage ou fallback local/base64. 5.4 Alarmes e notificações Retornos e recorrentes continuam usando a lógica de alarme original. O sino no cabeçalho concentra alertas internos. Configurações permitem controlar tipos de alarme, som, notificações do navegador e soneca. 5.5 Status e campos principais Área Valores Uso Etapa da solicitação nova, aguardando_info, aguardando_cotacao, em_elaboracao Colunas da Fila de Orçamentos. Status comercial da proposta aguardando_retorno, cliente_pediu_ajuste, sem_resposta, aprovada, recusada, nao_acompanhar Kanban de Propostas em Acompanhamento e histórico comercial. Status do pedido AG. APROVAÇÃO, APROVADO, REPROVADO, AG FATURAMENTO, FATURADO, APROV. MÊS SEGUINTE Controle de Vendas / planilha interna. Tipo de orçamento Peças, Serviço, Peças e serviço Classificação da solicitação e geração de linhas separadas no Controle de Vendas. Segurança, autenticação e regras externas A autenticação depende do Supabase Auth; o usuário precisa estar autenticado para acessar e salvar dados. A tabela de dados deve ter RLS permitindo acesso apenas a authenticated. O bucket agenda-dinamica-anexos deve permitir leitura/escrita de usuários autenticados. Anexos de clientes e solicitações não devem ficar públicos se contiverem informações sensíveis. Ao publicar no GitHub, revisar se chaves e URLs públicas do Supabase estão adequadas ao modelo de segurança. A anon key é pública por design, mas as permissões RLS são obrigatórias. Para produção, manter backup periódico dos dados JSON e revisar políticas do Storage. 11. Implementações já realizadas Migração de anexos para Supabase Storage, com fallback para anexos antigos. Guia de testes e manutenção Teste do fluxo principal Criar solicitação com cliente novo. Criar solicitação vinculando cliente existente. Anexar imagem e PDF. Mover entre colunas do Kanban. Registrar proposta enviada. Validar que aparece em Propostas em Acompanhamento. Validar que criou linha no Controle de Vendas. Atualizar status comercial. Atualizar status do pedido. Verificar Histórico e ficha do cliente. Teste de deduplicação Cadastrar cliente com CNPJ/e-mail/telefone já existente. Confirmar que o sistema vincula em vez de duplicar. Registrar proposta com mesmo nº/tipo/cliente. Confirmar que Controle de Vendas consolida a linha. Teste de anexos Anexar imagem na solicitação, salvar, reabrir e visualizar. Anexar PDF, salvar, reabrir e visualizar. Confirmar selo Storage quando o upload for bem sucedido. Teste de alarmes Criar retorno para hoje com horário próximo. Testar soneca. Validar alerta no sino e pop-up/alarme se permitido pelo navegador. Teste de exportações Exportar Controle de Vendas XLSX. Exportar relatório mensal comercial. Conferir status, valores e totalizadores. 14. Recomendações técnicas para próximas versões Consolidar funções duplicadas/overrides em uma versão única para reduzir risco de comportamento sobrescrito. Separar o arquivo em módulos: data.js, supabase.js, solicitacoes.js, clientes.js, controle-vendas.js, historico.js, styles.css. Criar uma camada única de estado e eventos para evitar múltiplos renderizadores conflitantes. Adicionar testes manuais documentados antes de cada subida no GitHub/Vercel. Manter changelog por versão antes de publicar em produção. Quando a ferramenta estabilizar, considerar uma refatoração para Next.js/React com componentes reutilizáveis e rotas organizadas.
